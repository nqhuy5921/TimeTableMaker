
- `typecheck` runs two configs: `tsconfig.node.json` (main, preload, shared, domain, tests) and `tsconfig.web.json` (renderer, shared, domain).
- The app reads `TTM_USER_DATA` to use a different data folder. End-to-end tests point it at a temp folder so they never touch real data.
- Electron 44 doesn't download its binary on `npm install`; it fetches it on first use, or with the install command above.
- Don't move to TypeScript 6.1 or 7 yet: `typescript-eslint` 8 supports only `<6.1`.

## Code layout

- `src/domain/`: the rules and types, plain TypeScript with no React or Electron. Every rule from the requirements lives here and is unit-tested here.
- `src/shared/`: the saved-file zod schema (typed against the domain model, so they can't drift) and the IPC contract.
- `src/main/` and `src/preload/`: the Electron main process and the `window.api` bridge. The renderer has no Node access (`contextIsolation`, `sandbox`, no `nodeIntegration`).
- `src/renderer/`: the React app. Design tokens are in `styles/tokens.css`.
- Imports between these folders are relative; there are no path aliases.

## Development lifecycle

Work moves through the phases below in order. Each phase has a gate: don't start the next phase for a feature until the current gate is met. A change that only fixes a bug or follows an approved design can go straight to implementation, but it still needs tests and a review.

| Phase | Output | Gate to move on |
|---|---|---|
| 1. Requirements | A written requirement per feature in `docs/requirements/`, with acceptance criteria | The user has approved the criteria |
| 2. Design | Architecture and data model in `docs/design/SYSTEM_DESIGN.md`, UI in line with `docs/design/DESIGN_SYSTEM.md` | The user has approved the design |
| 3. Implementation | Code in small steps that each leave the app working | Builds and lints cleanly |
| 4. Testing | Unit tests plus acceptance tests for every criterion from phase 1 | All tests pass |
| 5. Review | `/code-review` on the diff, findings fixed | No open correctness findings |
| 6. Release | Version number raised, changelog entry, Windows installer built | The user has signed off |
| 7. Maintenance | Bug fixes and yearly data updates, each starting again at phase 1 or 3 | — |

When you finish a phase, update **Current state** above so the next session knows where the project stands.

## Design system rules (from docs/design/DESIGN_SYSTEM.md)

Read `docs/design/TIMETABLE_SCREEN_LAYOUT.md` and `docs/design/DESIGN_SYSTEM.md` before any UI work. The layout spec wins where they disagree.

Keep the design files true (the user asked on 2026-10-21): any change that fixes or alters layout or visual style (sizes, widths, spacing, colors, type, columns, or what a screen shows) also goes into the design files in the same turn, without waiting to be asked. Screen layout goes in `docs/design/TIMETABLE_SCREEN_LAYOUT.md`, and shared rules (type scale, tables, buttons, tokens) in `docs/design/DESIGN_SYSTEM.md`. Each change gets a dated note saying the user asked for it. A CSS comment, a token in `tokens.css`, or a roadmap open item isn't enough on its own. Say in the reply which design file changed.

The rules that are easiest to break:

- All colors, spacing, radii, and shadows are CSS custom properties on `:root` in `src/renderer/styles/tokens.css` (per `docs/design/SYSTEM_DESIGN.md`, in place of the `style.css` path that `docs/design/DESIGN_SYSTEM.md` names). Don't write literal hex values. `--primary` is `#533afd`; the old `#4f46e5` must be replaced everywhere, including JS/HTML color-picker defaults. Likewise `--danger` is now `#ea2261`, replacing the old `#c0392b`.
- Subject colors come only from the 15 palettes in the layout spec (`COLOR_KEYS` in `src/domain/model.ts`, tokens `--subject-<key>-bg/-bar/-ink`). A subject's palette is set from its name by `defaultColorKey()`, unless the subject form picks one of the 15 palettes or Custom background and text (approved 2026-10-27, `SYSTEM_DESIGN.md` §10.5, built in R3-5b). Custom colors are user data, so they reach the screen as inline `--card-bg`, `--card-bar`, and `--card-ink`; the no-hex rule still holds for the app's own styles. The card form's "New subject…" offers no picker. `docs/design/DESIGN_SYSTEM.md` mentions High/Medium/Low clash severities, but the requirements use two levels instead: errors use `--danger`/`--danger-bg`, and warnings use `--warning-ink`/`--warning-bg`.
- Every numeric cell (counts, loads, period times) gets `font-feature-settings: "tnum"`.
- Buttons are always pills (`--radius-pill`), with at least `8px 16px` padding. The exceptions are the class tiles in the class bar, which are 8px-radius tiles (layout spec), and two controls from the approved release 2 design (added 2026-10-23, after the user asked for R2-2's review findings to be fixed): toggle chips, which are pills at the filter-chip size (`--chip-padding`, 6px 13px), and on/off switches, which are 34×20 pills with no padding (DESIGN_SYSTEM.md, Pill tags/chips and Toggles). Two more came with R2-5 (added 2026-10-23, after the user asked for its review findings to be fixed): the options of a full-width segmented switch, which keep 8px a side so "Warnings 12" fits the side panel, and the Issues tab's rows, full-width list-row buttons with `--radius-md` and `10px 12px` padding as the approved layout spec asks (DESIGN_SYSTEM.md, Segmented switches and List-row buttons). One more came with R3-5b (added 2026-10-27, after the user asked for its review findings to be fixed): the subject form's Colors row, a radio group of toggle-chip pills ("From the name", "Custom") and 24px round palette swatches with no padding (DESIGN_SYSTEM.md, Pill tags/chips, Color choices). One more came with R4-5 (added 2026-10-29, from the approved release 4 mockup): a dropdown menu's items, such as the Export menu's, are 14px rows with `8px 10px` padding and `--radius-sm` (DESIGN_SYSTEM.md, Menu items). Use one filled `--primary` button per screen region. Never use `--primary` for body text.
- The font is Lexend (300 body, 400 emphasis) with a `system-ui` fallback, bundled from `@fontsource/lexend` because the app is offline (NF-3). It includes the Vietnamese subset.
- Grid cells follow the layout spec: subject tint fill, ink text, an 8px `--danger` dot plus inset ring for a clash. Empty slots are white, with a faint midline in two-period blocks.
- The app header and the grid's day header are both `--header-bg` (`#6a3cbf`). The header is a bar across the top, not the left nav rail `docs/design/DESIGN_SYSTEM.md` describes. The class bar spans the width under it, and the 288px side panel sits left of the grid.
- Don't carry over anything from the marketing-site source system (gradient meshes, pricing cards, footer).

## The reference workbook

The workbook has 44 sheets. Text is Vietnamese, with many labels bilingual (`Vietnamese/ English`). The domain concepts the app needs map to these sheets:

- `TIMETABLE`: the daily bell schedule. Periods are paired blocks of 70 minutes (`1-2`, `3-4`, … `9-10`) with breaks between them, plus breakfast and morning assembly before period 1.
- `PPTL_XẾP TKB 26.27`: required periods per subject per week, broken down by class track and by half-term (`Nửa đầu/sau HKI/HKII`). A subject's weekly load can change between half-terms, for example physics swapping to chemistry.
- `Phan cong`: teaching assignments, one row per class and one column per subject, with teacher short names as values. It also lists the form teacher (GVCN) and co-teacher.
- `TK TIẾT GV`: per-teacher view grouped by department (`TỔ BỘ MÔN`), showing which class each teacher has in each day/period block.
- `HK1`: the master grid. Rows are day × period, columns are classes, and each slot is a subject row followed by a teacher row.
- `TKB 1S`: the same timetable flattened for export, with day codes `Th2`–`Th6`, period codes like `THCS12`, and subject plus teacher email per class.
- `ID GV 1S`: the teacher directory (full name, short name, email, main school vs. secondary school, role). Teachers can be shared between THCS and THPT.
- `Data `, `DS CLB phê duyệt`, `CT học các môn`: class contact info, approved clubs, and rotating-subject schedules by week.
- One sheet per class (`6A1` … `9BA1`): the printable per-class timetable, Monday to Friday, with form teacher contact details in the header. This is the target format for export.

How the sheets depend on each other, from their formulas:

- Typed by hand (the inputs): `TIMETABLE`, `PPTL_XẾP TKB 26.27`, `Phan cong`, `ID GV 1S`, `Data `, `DS CLB phê duyệt`, `CT học các môn`.
- `HK1`: the subject rows are typed by hand, and this is the work the app replaces. Each teacher row is an `HLOOKUP` of the class and subject into `Phan cong`. `COUNTIF` cells count each placement as a load or clash check, and about 400 of those formulas are broken (`#REF!`).
- Computed (the outputs): `TK TIẾT GV` reads from `HK1`. `TKB 1S` uses nested `XLOOKUP`s through `Phan cong` to `ID GV 1S` to get teacher emails. Each class sheet reads its cells from `HK1` and its header from `Data `.

Class names encode grade and track: grade 6–9 followed by a track code (`A`, `AA`, `CE`, `B`, `BA`) and a section number. Teachers are referred to by short name in grids and by email in the export sheet, so imports need to join through `ID GV 1S`.

The workbook contains real staff names, phone numbers, and emails. Don't copy it into fixtures or anything shared. Build anonymized samples instead.
